Architecture guide

Build, inspect, and understand LLM inference in Rust

A learning-oriented, production-shaped workspace built around mistral.rs embedded directly in-process — no server, no HTTP hop. Two applications, a CLI and a Tauri + Svelte desktop app, sit on the same backend-neutral core.

Running locally

Get it running first — the guide below explains what's happening under the hood.

Prerequisites

mistralrs is a plain crates.io dependency pinned to "0.8" (resolves to 0.8.1) — deliberately not the newer 0.9.x line; see the "Bugs found" entry below for why. First build still compiles the whole mistralrs-core/candle dependency tree, which takes a few minutes. Avoid running another cargo check/clippy/test at the same time as a build or a generation you're timing — that dependency tree is heavy enough that concurrent cargo processes will starve each other for CPU and make things look far slower than they are.

Overview

The rule that matters across this whole workspace: applications only ever know inferra-core's neutral types — GenerationRequest, GenerationResult, GenerationEvent, Usage — never mistralrs types, never Candle tensors. inferra-mistral is the only crate that imports mistralrs. That keeps the runtime replaceable (a direct Candle backend can implement the same InferenceBackend trait later) and gives every consumer — CLI, desktop, any future one — an identical API.

The boundary, compiler-enforced
CLI · Desktop · inferra-app · inferra-ui-bridge · inferra-coreonly ever see GenerationRequest / Result / Event / Usage
↓  the only crate with mistralrs in its Cargo.toml  ↓
inferra-mistraltranslates neutral types ↔ mistralrs types, one direction each way
↓
mistralrsthe actual SDK — RequestBuilder, SamplingParams, Response, …

Not a convention someone has to remember — no other crate's Cargo.toml lists mistralrs, so importing it anywhere else simply fails to compile.

Worked example

The NaN/Infinity bug, fixed in exactly one place

mistral.rs can report inf/NaN for a tok/s rate when a timing denominator is near-zero (see Bugs found) — a detail only inferra-mistral needs to know exists, because it's the only crate touching mistralrs's raw Usage struct.

crates/inferra-mistral/src/lib.rs
// Some(value) only if finite — None is the correct "not available"
// value here, not a workaround.
fn finite(value: f32) -> Option<f32> {
    value.is_finite().then_some(value)
}

Had mistralrs::Usage leaked into inferra-core directly, this same defensive check would've needed duplicating everywhere that read a rate: the CLI's printer, the Tauri bridge, the frontend's formatter. Instead it exists exactly once.

How inference actually works

Two very different phases hide behind one "Generate" button — and the prefill/decode split in Session metrics is those two phases, not two speeds at the same task.

The generation loop

→

→

→

↻

Decode loops — sample, feed the new token back in, decode again — until an end token or the token budget runs out.

Prefill: process the whole prompt at once

Every prompt token goes through all of the model's transformer layers in a single batched forward pass. This is compute-bound and highly parallel — the hardware is doing dense matrix multiplication across every prompt token simultaneously, so more tokens barely slows it down per-token.

Decode: generate exactly one token at a time

Each new token depends on every token generated before it, so these forward passes can't be batched the way prefill's can — one token in, one token out, every step, all layers, again. This is memory-bandwidth-bound, not compute-bound: the bottleneck is streaming the model's weights (and the growing KV cache) through memory once per token, not the arithmetic itself. That's the actual reason decode is slower than prefill on identical hardware — an inherent property of autoregressive generation, not an inefficiency.

The KV cache

Visible in every run's logs as "Prefix caching enabled": during prefill, the model computes a key and value vector for every prompt token at every layer and caches them. During decode, each new token only computes its own key/value and attends against the cache — it never recomputes attention over tokens already seen. Without it, decode would cost as much as reprocessing the entire prompt from scratch at every single step.

Sampling

Once the model produces logits — one score per vocabulary token — for the next position, SamplingParams decides which token actually gets picked. temperature rescales the logits before the softmax: 0 collapses it to always the single highest-probability token (greedy — our default). top_p (nucleus sampling) restricts candidates to the smallest set whose cumulative probability exceeds that threshold before sampling from it.

crates/inferra-mistral/src/lib.rs — build_chat_request
chat_request.set_sampling(SamplingParams {
    temperature: Some(options.temperature as f64),
    top_p: Some(options.top_p as f64),
    max_len: Some(options.max_new_tokens as usize),
    ..SamplingParams::neutral()
})

Bugs found & fixed

Discovered by testing against a real model, not assumed — each one changed how the code works, not just papered over a symptom.

Silent failure

mistral.rs's stream never sends a terminal Done

It just stops emitting Chunks, carrying usage/finish_reason on the last chunk instead. The original code only matched Response::Done, so it fell through silently — tokens streamed and printed fine, then nothing: no final result, no metrics. Fixed by accumulating text and last-seen usage as chunks arrive, treating stream exhaustion itself as the completion signal, and synthesizing Done — falling back to an actual Response::Done if one does show up on some path.

Silent failure

Non-finite tok/s rates broke JSON serialization

A near-zero timing denominator can make mistral.rs report inf/NaN for a rate, which serde_json refuses to encode — silently breaking the Tauri Channel send, which was itself being discarded with let _ = on_event.send(event). Fixed on both ends: map_usage converts any non-finite rate to None (the correct "not available" value), and the Tauri command now surfaces a send failure as a real error instead of swallowing it.

Display bug

A race between the terminal event and the invoke promise

busy was set to false when the outer invoke() promise resolved — not guaranteed to happen after the "Done" event had already set result. If the promise settled first, the UI briefly showed neither the streaming text nor the final result. Fixed by setting busy directly inside the Done/Error handlers.

Chart bug

The live chart rescaled to its own running max every frame

Both axes were normalized to the latest point's own value, so the newest point was always pinned to the right edge and older points kept shrinking left — reading exactly like the line growing backward. Fixed with a fixed pixels-per-second x-scale and a fixed token-budget y-scale (the request's actual max_new_tokens), so a point's position never moves once plotted.

Upstream bug — fixed in 0.9.3

Greedy sampling reported a "logprob" that wasn't one — confidence over 100%

The exact path, by type and field name: we call RequestBuilder::return_logprobs(true); streaming responses carry it on ChunkChoice.logprobs: Option<ResponseLogprob>, where ResponseLogprob { token: String, logprob: f32, .. } is the field we read. At temperature: 0 (this app's default), mistral.rs internally routes to sampler.rs::sample_argmax — and on the mistralrs 0.8 line that function never called softmax:

mistralrs-core/src/sampler.rs — sample_argmax (0.8.7, broken)
// "probs" is the raw model output — never normalized
let probs: Vec<f32> = logits.to_vec1()?;
let next_token = argmax_f32(&probs);
let logprob = probs[next_token as usize].log(10.0);

Working backwards from a real run's displayed value traced the exact bug:

We displayed446.2%
Our code: e^logprob4.462 → logprob = 1.496
mistral.rs: log10(x)x = 10^1.496 ≈ 31.3
31.3 isan ordinary raw logit — not a probability

A genuine log-probability requires softmax over the entire 49,152-token vocabulary first (p = e^logit / Σ e^logit_j) — sample_argmax was skipping that sum entirely and taking log10 of the raw winning logit directly, which is why the result could be positive (impossible for ln(p) or log10(p) when p ≤ 1). Confirmed, not just theorized: the same prompt at temperature: 0.7 (a real softmax-based sampling path, unaffected by the bug) produced correctly bounded, meaningfully-varying values — 22.8% for a less predictable word, 100.0% for a near-certain one.

Fixed defensively in inferra-mistral at the time via an is_greedy gate plus valid_logprob() rejecting any logprob > 0.0. Verified upstream against a local clone of mistral.rs at tag v0.9.3: sample_argmax now runs candle_nn::ops::softmax_last_dim before taking .ln(), so the value is a real log-probability at any temperature.

mistralrs-core/src/sampler.rs — sample_argmax (0.9.3, fixed)
let next_token = argmax_f32(&logits.to_vec1::<f32>()?)?;
let probs = candle_nn::ops::softmax_last_dim(&logits)?.to_vec1::<f32>()?;
let logprob = probs[next_token as usize].ln();

We briefly upgraded to a git dependency pinned to tag = "v0.9.3" once this was confirmed (crates.io only has mistralrs published through 0.8.1 — the 0.9.x line exists as GitHub tags only) and removed the is_greedy gate. That upgrade was reverted — see the next entry — so inferra-mistral is back on crates.io "0.8" and the is_greedy gate is back in place. valid_logprob()'s sign check stays regardless, as cheap defense-in-depth either way.

Upstream regression — reverted upgrade

0.9.3 fixed the logprobs bug but made unquantized CPU decode ~190x slower

After upgrading to confirm the fix above, real generation against an unquantized (fp16-in-GGUF, computed as BF16) model on this CPU-only Intel Mac went from usably fast to roughly one token every 20 seconds. Two false leads were ruled out first with direct evidence, not assumption: concurrent cargo builds competing for CPU (real, but not the whole story — the same slowdown reproduced with nothing else running, confirmed via ps/Activity Monitor showing a single process at 100% CPU and still far too slow), and Accelerate not actually being linked (otool -L confirmed it was).

The real cause: mistral.rs's own dtype-selection code (mistralrs-core/src/utils/normal.rs::determine_auto_dtype_all) has always special-cased the accelerate feature — #[cfg(feature = "accelerate")] return Ok(DType::BF16);, with the comment "we can safely use bf16 for accelerate because we cast up to f32 in all matmuls anyway." That code is byte-identical between mistral.rs 0.8.7 and 0.9.3 (checked directly against both tags), which ruled out mistral.rs's own logic as the cause. What differs is the candle-core/candle-nn git commit each version pins: 0.8.7 uses d2afd7f (v0.10.2), 0.9.3 uses 35d7ae7c (v0.11.0-dev) — so the "cast up to f32" upcast path in candle itself was the prime suspect.

Settled with a direct, isolated A/B test rather than more speculation — a standalone scratch binary built against each version, same model, same prompt, same token cap:

mistralrs 0.8.1 (candle d2afd7f / v0.10.2)9.50 tok/s decode
mistralrs 0.9.3 (candle 35d7ae7c / v0.11.0-dev)0.05 tok/s decode
Ratio~190x slower on 0.9.3

Quantized GGUF models (Q4_K_M etc.) are unaffected either way — they run through dedicated SIMD dequant-matmul kernels that never touch this dtype-selection path at all.

Decision: revert mistralrs to crates.io "0.8". For this app's actual use (a CPU-only learning box, unquantized models included), a ~190x decode regression is a bigger cost than a confidence report that's unavailable at temperature 0. To avoid a repeat of editing source every time this tradeoff gets re-evaluated, the is_greedy workaround is now gated behind a Cargo feature, greedy-logprobs (off by default, defined in inferra-mistral/Cargo.toml): a future re-upgrade to a mistralrs version with the fix (once the candle regression is also resolved upstream) is a config-only change — flip the feature on, no source edit needed.

Diagnostic, not a bug

Generation looked 300x slower — it was build contention, not a regression

Right after the 0.9.3 upgrade, a real run showed 4 tokens in 92 seconds — roughly 0.04 tok/s, against a measured ~12.8 tok/s decode on the same machine with accelerate enabled. Before assuming a real regression, both explanations that would actually matter were checked directly instead of guessed: does the built binary still link Accelerate.framework (otool -L confirmed yes), and does the accelerate feature still reach candle-core/candle-nn through the new git dependency (traced through mistralrs → mistralrs-core's Cargo.toml — yes, unchanged). Both ruled out a build misconfiguration.

Activity Monitor told the real story: nine separate rustc processes at 78–92% CPU each, all compiling the same heavy mistralrs-core/ candle dependency tree at once — leftover verification builds (cargo check/clippy/ test) running concurrently with the desktop app's own background rebuild and a live generation, all fighting for the same physical cores on one Intel Mac. The model wasn't slow; it was CPU-starved. Once the extra builds were stopped, generation returned to its normal rate.

Lesson for this workspace specifically: mistralrs-core is expensive enough to compile that running a verification build (cargo check/clippy/test) at the same time as measuring generation speed will make the measurement meaningless — the fix is to let one finish before starting the other, not to suspect the model or the hardware.

mistral.rs capabilities

Verified against the real mistralrs source, not assumed — some wired up already, some not yet.

Available

Per-token sampling knobs

top_k, min_p, frequency/presence/repetition penalty, stop_toks, logits_bias, DRY sampling — beyond the temperature/top_p/max_len we set today.

In use

Per-token log-probabilities

RequestBuilder::return_logprobs(true) returns each generated token's own probability — surfaced as the "Token confidence" report (Chat tab) and inline in the CLI's --stream output. Its top_logprobs alternatives only carry raw token IDs, not decoded text, so there's nothing honest to show for those — only the chosen token's confidence is real, displayable data. Only meaningful above temperature: 0 — see Bugs found.

Available

Custom logits processors

add_logits_processor accepts an Arc<dyn CustomLogitsProcessor> — an arbitrary hook into raw logits at every decode step.

In use

GPU / BLAS feature flags

metal, accelerate, mkl, cuda. Running accelerate after metal crashed at runtime on this machine's Intel/discrete-GPU combo.
